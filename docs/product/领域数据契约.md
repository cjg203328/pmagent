# 领域数据契约

Status: draft — 结构已定，**数值待业务方确认**
Owner: pmagent maintainers
Review cadence: 每次费率或资产分类调整时
关联：[`../product/PRD.md`](../product/PRD.md) §5 P0、§8、§12.1

## 0. 这份文档解决什么

当前人员费率在代码里存在 **4 处定义、零处互通**：

| 位置 | 形态 | 问题 |
| --- | --- | --- |
| `artpm_agent/skills/cost_control_skill.py:19-25` | 硬编码 dict：初级300/中级500/中高级700/高级1000/资深1500 | 与配置文件重复，改一处不影响另一处 |
| `artpm_agent/config_data/default_config.json:95` | `staff_levels` + `daily_cost` + **`min_days`** | 比硬编码版多一个字段，形状已漂移 |
| `staff.daily_cost` 列 | 数据库字段，8 列 | 只有 `MemoryManager.get_all_staff()` 读它；表 0 行 |
| `team_members.hourly_rate` 列 | 数据库字段，15 列 | 主链实际读的表，但**没有 `daily_cost`** |

结果是「给这个人排 3 个资产要多少钱」这类联合问题算不出来，因为任务分配读
`team_members`、成本计算读硬编码，两边不是同一批人。

本文件定义**单一权威来源**、字段语义、数据所有权和缺失时的行为。

## 1. 权威来源

**唯一费率来源：`team_members.daily_cost`。**

- `cost_control_skill.py` 的 `DEFAULT_STAFF_LEVELS` 常量 → **删除**。
- `config_data/default_config.json` 的 `staff_levels` → 降级为**首次播种用的默认值**，
  播种后不再被读取；文件头注明这一点。
- `staff` 表与 `task_assignments` 表 → **废弃**，`daily_cost` 并入 `team_members`，
  `contact_wecom` 并入 `team_members`。迁移步骤见
  [`../operations/收缩迁移手册.md`](../operations/收缩迁移手册.md)。
- `team_members.hourly_rate` → 保留为可选列，但**不参与计算**；`daily_cost` 是唯一
  计价口径，避免时/日换算歧义（当前代码用 `hours / 8` 隐含 8 小时工作日）。

技能层不得再自行持有费率默认值。取不到费率时的行为见 §6。

| `capacity_days_per_month` | numeric | ✓ | 月可用产能（人天），派单用 | ✗ 需新增 |

## 3. 技能档位

沿用现有 5 档命名，避免二次迁移：

`初级` / `中级` / `中高级` / `高级` / `资深`

档位只表示技能等级，**不表示雇佣关系**——费率由 §4 的供应商分层 × 档位共同决定。
当前代码把两者混为一谈（只有档位一档表），这是报价偏差的主要来源之一。

## 4. 供应商分层（待业务方填数）

美术外包的价差主要来自这里，通常 2–4 倍。当前代码完全没有这一维。

| 分层 | `employment_type` | 相对系数 | 典型场景 | 数值 |
| --- | --- | --- | --- | --- |
| 内部员工 | `internal` | 基准 ×1.0 | 长期在编，含社保与管理成本 | **待确认** |
| 签约工作室 | `studio` | 待确认 | 批量资产、稳定产能 | **待确认** |
| 自由职业者 | `freelance` | 待确认 | 单件、急件、特殊风格 | **待确认** |
| 海外供应商 | `overseas` | 待确认 | 汇率敏感、时区沟通成本 | **待确认** |

> ⚠ 系数**不由开发方推测**。需要业务方给出真实区间，或提供 3 份历史合同由我们反推。
> 在拿到之前，报价技能对非 `internal` 分层应返回 §6 的「缺数据」结果，
> 而不是套用内部费率。

## 6. 缺失数据时的行为（硬约束）

**不得用默认值静默补全。** 这是当前实现最大的可信度问题：
`cost_control_skill.py:43-46` 在读不到配置时直接回退到内置常量，用户和交付物
都不知道这个费率是猜的。

规则：

| 情况 | 行为 |
| --- | --- |
| 人员无 `daily_cost` | 返回 `needs_input`，列出缺哪个人，不产出报价 |
| 供应商分层无系数 | 同上，并说明该分层未标定 |
| 资产类型无基线 | 允许产出，但 `cost_source='default'` 且在交付物中显著标注「未经标定」 |
| 全部数据齐备 | `cost_source='contract'` 或 `'quote_history'` |

`needs_input` 对应 PRD §7.3 I5 的澄清卡片，不是错误。

## 7. 改稿与返工系数

美术外包的核心亏损项。数据列 `tasks.revision_count` **已存在**，成本公式里
却完全没有它。

| 参数 | 语义 | 数值 |
| --- | --- | --- |
| `included_revisions` | 报价内含的改稿轮次 | 待确认 |
| `revision_cost_ratio` | 每超一轮，增加该资产工时的一定比例 | 待确认 |
| `rework_trigger_ratio` | 超过几轮视为整件返工（按新件计价） | 待确认 |
| `avg_actual_revisions` | 历史均值，由 S3 复盘回写 | 由系统累积 |

S3 复盘的作用就是用真实 `revision_count` 持续修正 `avg_actual_revisions`，
再让下一次 S1 引用它——这是 PRD §3 里那条护城河回路的数据基础。

## 9. 数据所有权与更新节奏

| 数据 | 谁负责 | 更新节奏 | 出错影响 |
| --- | --- | --- | --- |
| 人员费率 `daily_cost` | 商务 / 制作人 | 合同变更时 | 直接进报价单，发给客户 |
| 供应商分层系数 | 制作人 | 季度 | 系统性偏差 |
| 资产工时基线 | 主美 / 组长 | 半年或工艺变更时 | 排期与报价双向偏差 |
| 改稿系数 | 系统由 S3 回写 | 每项目结束 | 长期收敛，短期不准 |
| 产能 `capacity_days_per_month` | 组长 | 月度 | 派单过载 |

**未决（PRD §12.1）**：费率数据是客户机密，人工录入还是从历史报价单反推？
这决定 §2 的 `cost_source` 以哪个值为主。

## 10. 落地顺序

1. Alembic 迁移：`team_members` 加 `daily_cost`、`capacity_days_per_month`、
   `cost_source`、`cost_effective_at`、`contact_wecom`。
2. 播种脚本：从 `default_config.json` 写入一次，标记 `cost_source='default'`。
3. 删除 `cost_control_skill.py:19-27` 常量与 `default_config.json` 的运行时读取路径。
4. 废弃 `staff` / `task_assignments`（见收缩迁移手册）。
5. 业务方填 §4 / §5 / §7 的真实数值。
6. 建立 `tests/golden/` 评测集，用真实报价单锁定正确性。

第 1–4 步是纯工程，可立即执行。**第 5 步依赖业务方，第 6 步依赖第 5 步**——
这两步不做，PRD 的 M2 之后所有里程碑都无法判定完成。
