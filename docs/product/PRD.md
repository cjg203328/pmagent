## 0. 一句话定位

**企业级业务助手 · 美术项目经理**：接住美术外包的报价、排期、进度、质控、交付与
复盘，以「任务」为单位交付可核验的文件成果，而不是以「对话」为单位生成文本。

界面形态同此定位：**三栏工作台（左任务 / 中过程 / 右成果）**，不是聊天窗口。
详见 §7。

**优先级次序（2026-09-19 确认）**：

1. **办公流任务优先**——agent 的第一职责是**把事做完并交付文件**，不是回答问题。
2. **知识库是支撑层，不是产品**——来源为企业 wiki 与个人经验总结两类，
   服务于第 1 条，不作为主交互入口。
3. **前期个人使用，后续扩展到团队**——多人能力保留但不投入。

这三条与现有代码形态**存在冲突**，见 §1.5。

## 1. 本次收缩的声明

定位从「通用 Agent 平台 + 薄业务壳」收缩为「单一业务角色的企业级助手」。

判据来自 2026-09-19 对 `data/` 的实测：

| 事实 | 数值 |
| --- | --- |
| 业务实体表 | 15 张中 14 张为 0 行（`projects`/`assets`/`tasks`/`quotes`/`deliveries`/`staff` 全空） |
| 工作流执行 | `workflow_runs=0`、`workflow_events=0`、`workflow_approvals=0` |
| 企业知识库 | `knowledge_resources=0`、`knowledge_versions=0`、`wiki_pages=0` |
| 审批请求 | `permission_requests=0` |
| 用户自建工作流 | 0 条（123 行全部 `source='builtin'`，见 §10 R-0） |
| 真实业务对话 | 18 个 user turn 中 3 条真实业务需求（2026-09-19 08:14–08:17），其余为模型连通、助手自述、单次文件生成冒烟 |
| 业务技能参与率 | 该 3 个回合 `intent=None`、`runtime_kind=local` → **9 个业务技能命中 0 次**，全部由 LLM 兜底 |
| 交付物产出 | 同期 `data/artifacts/` 新增文件 **0 个**；用户明确索要「仅11月汇总版」表格，最终只得到聊天内 markdown |
| 代码分布 | 业务技能 2,016 行 / 全仓 92,735 行 = **2.2%**；平台基础设施约 58% |

结论：**问题不是能力不够，而是没有一条链路被端到端跑过。** 因此本次收缩的主轴是
「接上，而不是加满」——复用既有管道，删除无人使用的横向能力。

## 1.5 与现有代码形态的三处冲突（必须先承认）

收缩主轴「接上而不是加满」对 S0/S1 成立，但对本节确认的三条优先级**部分不成立**。
逐条摊开：

**冲突 1：办公流优先 ↔ 办公流代码接近 0。**

| 栈 | 行数 | 占全仓 |
| --- | --- | --- |
| `memory/` + `retrieval/`（知识与记忆） | **14,219** | 15.3% |
| `evolution/` + `editing/`（反思/策略/蒸馏） | 3,133 | 3.4% |
| 办公流原语 | ≈0 | — |

办公流的"现有实现"只有两处字符串：`views/chat_welcome.py:38` 的一个「生成周报」
欢迎按钮，和 `routing/service.py:659` 的一个「交付台账」描述词。会议纪要、日程、
邮件、汇报、排班、考勤、采购在代码中**零命中**。

→ 办公流不是"接线"，是**新建**。这部分工作量必须显式排进里程碑，不能被
「复用既有管道」这句话掩盖。

**冲突 2：任务优先 ↔ `run_turn()` 的 handler 顺序相反。**

当前顺序（`harness/turn_service.py`）：

```
② try_knowledge_ingestion      :438  ← 知识入库
③ try_knowledge_rule_proposal  :450  ← 规则提议
④ try_artifact_generation      :460
⑤ try_workflow_routing         :467
⑥ try_skill_routing            :487  ← 业务/办公任务执行
```

知识捕获排在任务执行**之前**。用户说"帮我整理这周的周报"，系统可能先命中
知识入库或规则提议分支。

→ 需要显式的**意图优先级规则**（§4.5），这不是重构，是改判定顺序。

**冲突 3：知识库降为支撑层 ↔ 它是最大单一代码块。**

14,219 行的知识栈不会因此删除，但它的**入口**要从主交互退到被调用。
§8 相应改写：知识库不再作为用户主动查询的产品，而是任务执行时的上下文供给。

**这三条不改变收缩方向，但改变工作量估计**：§11 的 M1–M5 原本假设"接线即可"，
办公流部分需要真实的新建工作量。

## 2. 对标豆包工作：取其工作逻辑，不取其平台宽度

豆包工作（2026-08 发布，对标 WorkBuddy）的核心不是更强的聊天，而是六条工作逻辑。
逐条映射到本项目现状：

| # | 豆包工作的逻辑 | 本项目既有落点 | 缺口 | 本期动作 |
| --- | --- | --- | --- | --- |
| L1 | **任务是原子单位**，空间定边界 / 项目承目标 / 任务做执行 | `WorkflowRun` 模型已存在但 `run=0`；当前一等公民是 `conversation`/`message` | 缺「任务」这一层可寻址对象 | **新建 `Job` 聚合**，包装 `WorkflowRun`，成为 UI/API 主导航对象 |
| L2 | **交付成果而非回答**：标准卡片 / 云文档，团队可协作编辑 | `artifacts/` 已能产 DOCX/XLSX/PPTX/PDF 且复核页数、大小、SHA-256 | 交付物挂在消息里，不挂在任务上；无共享与再编辑 | 交付物归属改为 `Job`；新增成果清单与版本追加 |
| L3 | **从写材料到管流程**：长程多 Agent 并行 | `runtime/subagent.py` + AgentLoop 有界 worker/超时/取消 | 无跨天/跨会话的续跑；无流程模板 | 任务状态机支持 `waiting/scheduled`；内置 1 条 5 阶段真流程 |
| L4 | **定时自动化**：无人触发的周期任务 | `evolution/scheduler.py:156 run_if_due()`、`outbox_worker.py` 租约/指数退避/死信 | 原语齐备但只服务内部反思与索引投影 | 复用同一 worker 骨架，接入「每日进度巡检 + 催办投递」 |
| L5 | **权限自动继承**，数据按登录身份隔离 | `tenancy/` + `permission_store` + 可信 `(tenant, workspace)` + RLS | 权限粒度是"能不能调工具"，不是"能不能看这个项目" | 授权对象下沉到 `Job`/`Project`；审批边界保留不变 |
| L6 | **知识边界 = 空间边界**，全端接续 | `WorkspaceKnowledgeStore` + `RetrievalPlan/Hit` + SSE `run_id`/断点续传 | 库里 0 份知识；引用不进交付物 | 知识库改「导入即产出引用」；引用写入成果文档 |

**明确不学**：豆包工作的通用入口矩阵（PC/主对话/第三方 IM）、视频生成、消费级流量
运营、开放平台生态。本项目是单机可部署的窄域助手。

## 3. 目标用户与场景

### 主要用户

- **美术外包项目经理 / 制作人**（唯一主角色）：对接甲方需求、盯供应商产能、控改稿
  成本、按期交付。日常动作是「算报价、排人、催进度、验收、写复盘」。
- **次要**：外包团队负责人（被派单、被催办）、商务（发报价单）。

### 场景优先级（S0 来自实测，排在 S1 之前）

**S0 表格清洗 → 导出新文件**（2026-09-19 真实发生）
上传 `角色组-任务及绩效分配.xlsx`（163 KB，真实美术团队人天表）→ 理解结构 →
按月份裁剪 → 产出「仅11月汇总版」**文件**。
*实测失败点*：`parsers/excel_parser.py:116` 把该文件硬编码分类为 `"报价单"`；三个回合
`intent=None`，未命中任何业务技能；08:16 助手明确回答「我无法直接把原附件另存/导出成
'只含11月'的新文件」；08:17 用户坚持后仍只得到聊天内 markdown，`data/artifacts/`
零新增。
*验收*：同一份表、同一句「要仅11月汇总版」，产出一个可下载的 `.xlsx`，且保留原表头格式。

**四个必跑通的场景**

> 业务场景（S1–S3）与办公流场景（S4）是**两族**，共用同一套 `Job` + 交付物管道。
> 按 §0 优先级，办公流优先——但它的技术前置（R-4 交付物接通、`Job` 对象）
> 恰好由 S0/S1 最先暴露，因此排期上 S0/S1 先行，见 §5 的依赖说明。

**S4 办公流（优先族，见 §4.5 技能清单）**
一句话生成周报 / 会议纪要 / 台账更新 / 待办分派 / 通知拟稿，**产出可发送的文件**
而不是聊天文本；过程中自动引用企业 wiki 与个人经验。
*现状*：办公流原语在代码中接近 0（§1.5 冲突 1），`chat_welcome.py:38` 只有一个
「生成周报」按钮，无实现。
*验收*：说「生成这周周报」，得到一份 `.docx`，内含本周任务进展、风险与下周计划，
且引用了本周实际会话与 `tasks` 变更。

**S1 报价测算 → 交付报价单**
丢进甲方 Excel/PDF 需求表 → 按资产类型拆解工时 → 匹配供应商分层费率 → 计入管理费、
税、**改稿预算**、账期 → 产出可发送的《报价单.docx》并附计算依据引用。
*验收*：项目经理愿意把这份文件原样发给客户。

**S2 排期派单 → 每日巡检 → 催办**
确认报价后生成任务图 → 按 `daily_cost` 与在手工时排人 → 每日定时巡检临期/延期 →
生成催办并投递企业微信 → 成员回传进度写回 `tasks`。
*验收*：连续 5 个工作日无需人工干预即可产出正确的催办清单。

**S3 验收复盘 → 沉淀为下一条报价的依据**
交付后按 `revision_count` 与 `actual_hours` 对比估算 → 产出《复盘报告.docx》 →
把"这类资产实际比估算多 X 稿"写为知识规则 → 下一次 S1 自动引用该规则。
*验收*：第二次报价的估算偏差显著小于第一次。

S3→S1 的回路是本产品的护城河。没有这个回路，它只是一个会写文档的聊天机器人。

## 4. 核心对象模型改造（结构性工作之一，另一项见 §4.5）

现状：`conversation` → `message` →（偶尔）`artifact`。
改为：`workspace` → `project` → `job` → `step` → `artifact`，对话降级为 job 的一个通道。

```text
Workspace（权限与知识边界，已有）
└── Project（projects 表，已有但空）
    └── Job ← 新增一等公民，包装 WorkflowRun
        ├── trigger      手动 / 定时 / 来自消息
        ├── inputs       附件快照、结构化参数、引用的知识规则
        ├── steps[]      复用 WorkflowStepRun
        ├── artifacts[]  复用 artifacts/ 生成 + 核验，归属改为 job
        ├── approvals[]  复用 WorkflowApproval
        ├── status       draft/queued/running/waiting/succeeded/failed/needs_input
        └── thread[]     关联消息（对话成为可选通道，不是容器）
```

约束：

- `Job` 必须可在无人对话时被创建、推进、完成（定时触发即可）。这是「任务而非对话」
  的硬判据。
- 一个 `Job` 的全部读写继续携带可信 `(tenant_id, workspace_id)`，不得新增旁路。
- `run_turn()` 仍是唯一执行入口。`Job` 是**编排层**，不新增第二条业务主链。

## 4.5 意图优先级规则（办公流优先的落地机制）

「优先用 agent 解决办公流任务」必须变成可判定的路由顺序，否则只是一句口号。

### 判定次序

```
输入
  │
  ├─ 命中「任务动词」？  生成/整理/汇总/导出/裁剪/排期/催办/发送/归档/对比
  │     是 → 建 Job，走执行链（办公流 / 业务技能 / 交付物）  ★最高优先
  │     否 ↓
  ├─ 命中「知识写入意图」？（"请记住…"、上传需归档的资料）
  │     是 → 知识入库 / 规则提议（需确认）
  │     否 ↓
  ├─ 命中「查询意图」？（"…是什么"、"有没有过…"、"上次…"）
  │     是 → 知识库检索，作为**回答的引用来源**，不建 Job
  │     否 ↓
  └─ 通用对话兜底（LLM）
```

### 三条硬规则

| # | 规则 | 反例（当前行为） |
| --- | --- | --- |
| P1 | **执行意图先于捕获意图。** 同一句话既要归档又要产出文件时，先产出文件，把归档降为任务收尾的可选建议 | `try_knowledge_ingestion` 在 `:438`，`try_skill_routing` 在 `:487` |
| P2 | **执行意图先于检索。** 需要文件产出时，检索只作为 step 的输入，不单独成答 | 检索命中即返回文本答案 |
| P3 | **知识检索不得成为终答。** 纯问答路径的回复必须标注引用来源；若用户实际要的是文件，提示「是否生成 XX 文档」并一键转 Job | 问答与任务在 UI 上无法区分 |

### 与 handler 顺序的映射

`run_turn()` 的 handler 次序需要按 P1/P2 重排为：

```
Step 0  记忆/上下文注入
Step 1  ★ 任务执行族：artifact 生成 → 工作流 → 业务技能 → 办公流技能（新增）
Step 2  知识入库 / 规则提议（降为收尾建议）
Step 3  模型兜底
```

这是**改判定顺序 + 新增办公流技能族**，不是重写主链。`run_turn()` 仍是唯一入口。

### 办公流技能族（新增，非接线）

| 技能 | 产出 | 优先级 |
| --- | --- | --- |
| `weekly_report` 周报 | `.docx` / 企业微信摘要 | **P0**（`chat_welcome.py:38` 已有按钮但无实现） |
| `meeting_minutes` 会议纪要 | `.docx`，含决议与待办抽取 | P1 |
| `todo_dispatch` 待办分派 | 写入 `tasks` + 催办 | P1 |

| `notice_compose` 通知拟稿 | 企业微信投递 | P1 |
| `doc_organize` 文档归档整理 | 目录方案 + 批量入库 | P2 |

## 6. 交付物规范

每个 `Job` 至少产出一个可核验文件，规则沿用 `docs/architecture/ARTIFACT_GENERATION.md`：
重新打开产物核对页数/工作表/段落与请求文本，校验发布副本大小与 SHA-256，仅

## 8. 知识库范围（支撑层，不是产品）

**定位**：知识库不作为用户主动查询的主入口（那是 §4.5 P3 的约束），而是任务执行时的
上下文供给。它的两条来源可见范围不同，**不得合并成一个库**。

### 两个来源

| 来源 | 内容 | 可见范围 | 写入方式 | 团队阶段 |
| --- | --- | --- | --- | --- |
| **企业 wiki** | 流程规范、验收标准、命名规范、术语表、组织架构 | workspace 内共享 | 导入 + 人工维护 | 后续成为团队共用层 |
| **个人经验总结** | 个人报价心得、供应商评价、踩坑记录、历史偏差结论 | **仅本人** | 任务收尾时提议沉淀（§4.5 P1） | 后续需显式「共享给工作区」才升级 |

`views/wiki.py`（279 行）与 `memory/wiki_store.py`（1,399 行）已具备企业 wiki 侧能力，
但 `wiki_pages=0`。个人经验侧目前与知识规则混在 `knowledge_rules` 一张表里，
**需要新增 owner 维度区分可见性**——这是"前期个人、后续团队"必须现在埋好的唯一一件事
（§12.2）。

### 三类内容

1. **费率与产能**：供应商分层价、人员日费率、历史工时偏差。结构化，S1 直接读取。
   权威定义在 [`领域数据契约.md`](领域数据契约.md)，知识库只存历史与偏差。
2. **流程与规则**：验收标准、改稿上限、命名规范。来自企业 wiki 与 S3 复盘回写。
3. **历史项目档案 + 个人经验**：报价单、合同、需求文档、复盘报告，以及个人总结。
   向量索引仅为加速层，字面检索兜底，索引可全量重建。

### 与办公流的关系

办公流任务大量消费知识库：周报要读本周任务与纪要、会议纪要要读参会人与历史决议、
台账要读项目档案。因此知识库的**验收标准是"任务是否因此做对了"**，
不是"检索命中率"或"问答质量"。§9 指标据此设定。

### 不做

通用网页采集、GraphRAG、跨租户共享知识、把个人经验默认暴露给全工作区。

### R-0 原始记录

`definition_json` 内含 `"version": N`，而 checksum 覆盖整段 JSON。`defaults.py` 声明
版本恒为 1，存储 checksum 每次不同，`store.py:386` 判定"builtin 已变更，发布下一版"，
每次启动为 3 个流程各写一行新版本并复制 override。实测单日从 111 行增至 123 行。

### R-5 细节（本轮新发现，值得留档）

真实附件 `角色组-任务及绩效分配.xlsx` 的月份在 **sheet 名**上
（`24年11月`、`25年1月`…共 13 个），行是任务、列是人名。而
`transform_monthly_workbook` 只认「月份列 + 逐行日期」的长表形状，于是对真实输入
直接报「没有找到 11月 的数据」——**功能测试全绿，真实数据一条都跑不通**。

修法：`sheet_target_month()` 识别 sheet 标题里的月份（支持 `24年11月` 与 `2024-11`），
`_select_sheets_by_month()` 按表名取舍，无月份的表保留（无法判定时删表是更坏的错误）；
`resolve_target_month()` 从工作簿实际用到的年份消歧，跨年冲突时要求指定年份而不是猜。

教训：**任何只调用库函数、不走 `run_turn`/HTTP 的测试，都不能证明功能可用。**
M1 之后新增的能力必须至少有一条端到端断言。

### §4.5 落地形态与剩余边界

执行意图优先门已实现（2026-09-20），形态是**动词门**而非物理重排：
`turn_service._EXECUTION_INTENT` 命中时跳过两个知识捕获 handler，让执行族
（artifact → workflow → skill）先跑；无执行动词时捕获 handler 保持原有顺序。
选这个形态是因为物理重排会让技能关键词劫走「记住上次的报价要加管理费」这类
捕获意图——决策树的语义是「任务动词 → 执行；否则 → 捕获」，不是简单的先后交换。
回归：`tests/test_intent_priority_gate.py`。

办公流技能族首个成员 `weekly_report` 已交付（M3.5），且它现在会登记 Job 并把交付物
挂在 Job 名下（`JobService.create` → `attach_artifact` → `transition(succeeded)`），
办公流与任务模型不再是两条平行线。Job 的公开面为 `GET /v1/jobs`、
`GET /v1/jobs/{id}`、`POST /v1/jobs`（`api/routers/jobs.py`）。

剩余：三栏 UI 骨架未做（①栏尚未渲染 Job 列表）；`ledger_update`、
`meeting_minutes`、`todo_dispatch`、`notice_compose` 未建；S1 端到端未做。

### 已排除的怀疑

`JobService` 曾被怀疑缺少租户隔离。实测结论是**隔离正确**：
`tenant_session._context_for()` 在 session 未显式绑定上下文时回退到
`TenantContextManager.get_current()`；租户 A 的 `list()` 只返回 A 的行，
跨租户 `get()` 抛 `JobNotFoundError`，无上下文时返回空。
`JobService` 未接入生产入口属 M2 功能范围，不是缺陷。

### M1.5 spike 结论（2026-09-20 实测）

问题：Streamlit 能否承载「左任务 / 中过程 / 右成果」且各栏独立滚动？

**答案：可以，且不需要自定义组件。** Streamlit 1.59 的
`st.container(height=..., autoscroll=...)` 原生提供独立滚动区。spike 应用用
`st.columns([3,2,2])` + 每栏一个 `height=420` 的容器，浏览器 DOM 实测：
三个 `overflow-y: auto` 区域，把第一栏 `scrollTop` 设为 300 后，另两栏仍为 0。
因此 PRD §7.4 R-UI 的「固定成果栏 + 独立滚动」在原生 Streamlit 下成立，
**不需要** iframe、独立页或脱离 Streamlit。PRD §12.3 的形态决策可以关闭：留在 Streamlit。

残留限制：页面整体仍会随浏览器滚动；若三栏总高超过视口，需要把三栏放进一个
`height=100vh` 的外层容器才能让页面本身不滚。M2 实现时验证。
