# 交付物模板库

Status: current（引擎现状）+ draft（业务模板待业务方确认字段）
Owner: pmagent maintainers
Review cadence: 新增交付物类型或版式变更时
关联：[`../product/PRD.md`](../product/PRD.md) §6、[`领域数据契约.md`](领域数据契约.md)

## 1. 定位

PRD §2 L2：交付成果而非回答。本文件定义**业务文档**的字段、版式和引用规则。

它不是引擎文档。生成与核验机制见
[`../architecture/ARTIFACT_GENERATION.md`](../architecture/ARTIFACT_GENERATION.md)。

## 2. 引擎现状（已具备，不要重复实现）

`artpm_agent/artifacts/generator.py` 已支持：

| 方法 | 能力 |
| --- | --- |
| `generate_xlsx` / `generate_docx` / `generate_pptx` / `generate_pdf` | 从零生成 |
| `generate_xlsx_from_template` / `generate_docx_from_template` | 按模板生成 |
| 格式转换 | `xlsx→csv`、`csv→xlsx`、`xlsx/csv/md/txt→docx` |

`artpm_agent/artifacts/templates.py` 做的是**反向**能力：从用户上传的
`.xlsx/.xlsm/.csv` 中抽取表头、工作表与样例行，形成可复用模板
（上限：8 sheet / 120 列 / 80 段 / 名称 80 字符）。

核验：重新打开产物核对页数、幻灯片、工作表或段落与请求文本，校验发布副本大小与
SHA-256；仅 `verification.status=passed` 才进入下载卡片。

**结论：引擎够用。缺的是业务模板定义和「让业务请求命中它」的路由**
（后者是 PRD §10 R-4，M1 修）。

## 3. 通用规则（所有模板强制）

| # | 规则 | 理由 |
| --- | --- | --- |
| G1 | 必须内嵌**计算依据**：费率来源、工时来源、引用的知识规则 ID | 只给结论的文件不可复核，客户一问就崩 |
| G2 | 必须标注数据时效：`cost_effective_at` 与生成时间 | 费率过期是真实纠纷来源 |
| G3 | 未经标定的数值必须显式标注「默认值/未标定」 | 对应领域数据契约 §6 的 `cost_source` |
| G4 | 同一 Job 重跑**版本追加**，不覆盖历史成果 | 报价改过几版必须可查 |
| G5 | 页脚含：项目名、工作区、生成者、Job ID、核验状态 | 可追溯 |
| G6 | 金额一律保留 2 位小数并标币种；人天保留 1 位 | 避免下游对不齐 |

## 4. T1 报价单（S1 主交付物）

格式：`.docx`（可发送客户）。数据表另存 `.xlsx` 附件。

```text
封面：项目名 / 甲方 / 报价编号 / 报价日期 / 有效期 / 联系人
一、需求概述        资产范围、数量、风格参考、验收标准来源
二、报价明细表      见下表，逐资产类型一行
三、费用构成        人工 / 管理费 / 税 / 改稿预算 / 加急 / 小计 / 总计
四、工期与里程碑    分段工期、交付节点、甲方反馈窗口
五、付款条件        分期比例、账期、质保金
六、假设与边界      内含改稿轮次、超出如何计价、不含事项清单
七、计算依据        费率来源表 + 引用知识规则 ID + 未标定项声明
```

明细表列定义：

| 列 | 来源 | 必填 |
| --- | --- | --- |
| 资产类型 | `assets.asset_type` | ✓ |
| 复杂度 | 需求评估技能 | ✓ |
| 数量 | 甲方需求表 | ✓ |
| 单件工时(人天) | 领域数据契约 §5 基线 | ✓ |
| 承接方 | `team_members` + `employment_type` | ✓ |
| 人天费率 | `team_members.daily_cost` | ✓ |
| 小计 | 计算 | ✓ |
| 内含改稿轮次 | 领域数据契约 §7 | ✓ |
| 依据 | `cost_source` + `cost_effective_at` | ✓ |

> ⚠ 字段待业务方确认。当前 `cost_control_skill` 的公式**尚不能产出**第四~六节
> 所需的改稿、账期、加急、质保金数据（领域数据契约 §7、§8）。

## 5. T2 人天/产能汇总表（S0 主交付物）

格式：`.xlsx`。这是 PRD §10 R-4 要立刻打通的第一个模板。

| 列 | 说明 |
| --- | --- |
| 任务 | 原表任务名 |
| 商务人天 | 合同/报价口径 |
| 已分配人天 | 排期实际占用 |
| 差异 | 已分配 − 商务 |
| 状态 | 未开始分配 / 未启动 / 存在挪用缺口 / 轻微差异 / 进行中 |
| 说明 | 差异原因 |

规则：

- **保留原表表头格式与列宽**（实测需求来自 `角色组-任务及绩效分配.xlsx`）。
- 按月份裁剪时，明确区分「本月新增」与「含上月结转的累计值」——实测中这一混淆
  导致 19 人天被当成新增。必须在表注中写清口径。
- 未覆盖的行数在表注中声明（实测回答里出现过「未覆盖全部 15 个任务」）。

## 6. T3 复盘报告（S3 主交付物）

格式：`.docx` + 回写 `knowledge_rules`。

```text
一、估算 vs 实际        逐资产类型对比工时与改稿轮次
二、偏差归因            工艺难度 / 需求变更 / 改稿超限 / 人员产能
三、费率修正建议        写入知识规则的候选值（需人工批准）
四、供应商表现          质量分、准时率、改稿率
五、下项目调整项        自动被下次 S1 引用
```

关键：第三节产出的必须是**结构化知识规则**（带 `workspace_id` 与生效条件），
不是散文。否则 S3→S1 回路断掉，PRD §3 的核心价值不成立。

## 7. T4 催办通知（S2 交付物）

格式：企业微信文本 + 存档 `.md`。

| 字段 | 说明 |
| --- | --- |
| 收件人 | `team_members.contact_wecom`（从 `staff` 并入） |
| 任务 | 任务名 + 截止日 |
| 逾期天数 | 计算 |
| 当前进度 | `tasks.progress` |
| 回复要求 | 明确动作与时间 |

投递结果必须回写 `reminders.sent_status`。当前 `reminders` 表 0 行，
该模板未接通。

## 8. 模板存储与版本

- 内置模板：`artpm_agent/config_data/` 下按 `T1..T4` 定义，随版本发布。
- 用户模板：从上传文件抽取（`extract_spreadsheet_template`），存
  `WorkspaceKnowledgeStore`，带 workspace 隔离。
- 模板变更走版本号，不改历史；报价单交付物必须记录所用模板版本（G4 的一部分）。
